# 09 · 深度改造 opencode：性能导向的 Fork 路线

## 1. 先算账：瓶颈在哪

典型建模会话的耗时分布（**量级估算，P1 埋点实测后修订**：每会话记录 LLM 时延 vs 工具时延直方图）：

| 环节 | 量级 | 占比（估） | 影响 |
|---|---|---|---|
| LLM 推理（每轮 2–10s × 30–80 轮） | 分钟级 | ~90%（估） | 主导 |
| 截图 token（每张 500–1500 tok × N 步） | 隐性大头 | — | 占满上下文窗口→触发压缩→进一步拖慢 LLM |
| COM 操作（sidecar 串行执行） | 10–100ms/步 | ~2%（估） | 单文档可忽略；多文档下叠加激活切换 100–500ms/次（[12](./12-multi-workpiece.md) §2），占比上升 |
| HTTP/fetch 开销 | ~1ms | 忽略 | — |

**结论：深改的目标不是"让工具更快"，而是减少 LLM 轮次、削减 token（尤其图像）、提高缓存命中。**

## 2. 七个改造方向（按收益排序）

| # | 方向 | 改什么 | 插件层能做到吗 | 预期收益 |
|---|---|---|---|---|
| 1 | **图像上下文管理** | 历史截图自动降采样→只留最近 K 张全分辨率，旧图替换为特征树 diff 文字 | 勉强（`experimental.chat.messages.transform` 可改写消息 parts，但有拷贝开销且 input 无 sessionID） | **token −50~70%**，上下文寿命 ×3 |
| 2 | **CAD 专用压缩** | 压缩时丢弃全部过程对话，重建为"用户需求 + 特征树状态 + 未完成意图"——sidecar 状态即 ground truth，近乎无损 | 部分（`experimental.session.compacting` 钩子有限，压缩摘要仍由 LLM 生成） | 长会话不发生压缩级联，30 步以上任务必需 |
| 3 | **多模型分工** | 截图核验路由到小模型（快/便宜），规划用强模型 | ✅（**插件层可实现**：`cad-verifier` subagent 显式配便宜 vision 模型 + task 派发；或 `experimental.provider.small_model` 钩子） | 每轮验证 −1~3s，成本 −60% |
| 4 | **链式执行与断点续跑** | 模型一次发 [sketch_entity×N, feature] 链，sidecar 全链执行，仅失败处中断回传——省去"每步都回 LLM 确认" | ❌（loop 逐 tool 回传结果） | **轮次 −40~60%** |
| 5 | **Prompt cache 工程** | 保证消息序列化顺序稳定（schema 排序冻结、指令放尾部） | 部分（`tool.definition` 钩子可冻结 schema 顺序） | 缓存命中 → 首token延迟 −30% |
| 6 | **流式工具调用** | tool_use JSON 流式解析，参数齐了就提前 fetch sidecar | ❌ | 每轮 −200~500ms |
| 7 | 二进制裁剪 | 移除 TUI/分享等无关模块重编译 | ✅（但没意义） | 体积小，性能无感 |

## 3. 四个核心改造的设计要点

### 3.1 图像生命周期管理（改消息组装层）

```
消息历史中的 image part 生命周期：
新截图(全分辨率) → 上一轮之后(降到 512px) → 更早(替换为 "[图:拉伸1完成，特征数6]")
+ 每次轮次开始前按 token budget 从最旧开始回收
```

原理：模型只需要"看清最近一步、记住更早步发生了什么"。这是纯 CAD 领域知识，通用 agent 框架不会内置——**这正是 fork 的正当性所在**。

### 3.2 以 sidecar 状态为锚的压缩（改 compaction 流程）

默认压缩 = 让 LLM 总结对话（有损、慢、丢参数）。CAD 场景下 `/state` + 特征树 diff 就是精确历史，压缩退化为：拉取 sidecar 快照 + 保留最近 3 轮原文 + 用户原始需求，其余全丢。零 LLM 成本、零信息损失（模型可随时 `sw_get_state`）。

### 3.3 双模型验证回路（模型路由）

```
强模型：规划、草图设计、读最新全分辨率截图
小模型：批量核对历史截图 vs 意图清单（yes/no + 偏差描述）
```

把"每步都让强模型看图"变成"强模型只看当前步，小模型巡检历史"。

**实现路径修正**：此项**插件层即可落地**——定义 `cad-verifier` subagent（agent 文件显式配置便宜 vision 模型；subagent 默认继承 primary 模型，必须显式指定），强模型经 task 工具批量派发核对任务。fork 不是必需；fork 版的增量仅在于让路由对 LLM 透明（无需在上下文里维护 verifier 的调用协议）。

### 3.4 链式执行（改 agent loop）

模型输出带依赖标注的操作清单 → fork 的执行器直接全链提交 sidecar（串行队列天然支持）→ 全链完成或失败处截断，一次性回传结果集。配合 sidecar 的 generation 校验，中间无需 LLM 参与。失败时只回传失败点前后的 state diff + 截图，模型从断点续跑。

> 链式执行与 [12-multi-workpiece.md](./12-multi-workpiece.md) 的文档亲和调度天然协同：整条链在同一个亲和批内执行 = 零额外激活开销。

## 4. Fork 工程策略（防止 fork 失同步）

1. **薄 fork**：改动只许落在四个模块——agent loop、消息组装、compaction、模型路由（方向 3/6 的落点）。以 `fork/patches/` 维护，目标 <3000 行改动，每 minor 版 rebase 上游
2. **全特性挂 flag**：`CAD_LOOP_V2`、`CAD_IMAGE_GC` 等环境开关，关掉即回到原生行为——保证 bug 可二分、可降级
3. **插件层等价物保留**：方向 1/2/3/5 用钩子/subagent 各写一个降级实现；主程序启动时探测 fork（fork 版经环境变量 `OPENCODE_BUILD=cad-fork` 自标识），非 fork 走插件降级路径（功能在，性能打折）
4. **上游化策略**：通用能力增强（如消息变换钩子补 sessionID、压缩钩子扩展）以 PR 回馈上游——fork 里只留 CAD 特化逻辑，rebase 面随时间收敛
5. **CI 双轨**：同一测试集跑原生 opencode + fork，防 rebase 回归

## 5. 决策建议

| 场景 | 建议 |
|---|---|
| P1/P2 阶段 | **不 fork**。插件层先做：双模型（subagent）+ 钩子降级版图像管理 + AGENTS.md 引导串行，可先拿到约一半收益 |
| 出现以下信号再 fork | ① 任务平均 >40 步、上下文频繁压缩级联；② 图像 token 成本显著；③ 用户对"每步停顿"有明确抱怨 |
| Fork 顺序 | ② CAD 专用压缩 → ① 图像GC → ④ 链式 → ⑥ 流式解析（前两个纯收益低风险；后两个动 loop 需回归测试。方向 ③ 双模型已移出——插件层即可实现） |

**一句话：深改的性能红利几乎全部来自"CAD 领域知识下沉进 agent loop"——图像会过期、状态有权威源、操作可成链。这些通用框架不会替你做，做进去的那一刻，fork 才有意义。**
